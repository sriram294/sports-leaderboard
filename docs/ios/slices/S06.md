# S06 — Notifications and app updates

## Outcome

Users can grant notification permission, register/unregister an iOS device, route supported pushes, and receive platform-specific update prompts.

## Entry criteria

S05 is merged and closed by the first transition commit on `feature/ios-notifications`; S06 is the only `in_progress` slice.

## Scope

Initialize Firebase Messaging only after configuration validation, implement APNs/FCM token lifecycle and deep-link routing, notification settings/recovery, and iOS app-update checks/prompts.

## Public contracts

Add `GET /api/v1/app/update?platform=ios`. Extend device registration to accept `platform: "ios"` while preserving Android compatibility. Document push payload routing/versioning.

## UX and state contract

Cover undetermined/denied/authorized/provisional notification states, settings deep link, token refresh, offline/failure retries, foreground/background routing, unknown payloads, optional/required update prompts, VoiceOver, and both appearances.

## Architecture and tests

Inject notification center, messaging token source, device repository, update repository, application opener, and clock. Unit-test lifecycle races and routing; backend integration tests cover platform contracts; UI tests use adapters and never require real push credentials.

## Exclusions

Distribution signing, App Store publication, and account deletion.

## Verification evidence

Record iOS/backend suites, `.xcresult`, JUnit, payload fixtures, permission-state screenshots, and a secret scan proving APNs/Firebase material is absent.

## Exit criteria

Device/update contracts are backward compatible; notification/update flows handle all permission and failure states; provider configuration remains external.

## Next transition

Create `feature/ios-account-lifecycle`; record S06 PR/merge evidence, mark S06 `done`, and start S07.
